# Серверная оптимизация olcRTC

**Статус:** согласованный дизайн, 2026-11-20
**Репозиторий:** `ghostlane-project/olcrtc`, ветка `proofkit`

## Цель

Увеличить полезную пропускную способность серверного olcRTC и снизить нагрузку на ВДС для Mamba/DataChannel и VK Calls/VP8, не меняя wire-протокол и не требуя синхронного обновления клиентов.

Сначала измеряется фактическое узкое место. Изменение принимается только при подтверждённом улучшении и отсутствии регрессий стабильности.

## Что не входит

- Bonding и scheduler комнат в приложении.
- Изменения подписки, Xray, роутера и Russia-direct.
- Удаление base64 из Jitsi EndpointMessage: JVB требует этот формат.
- Изменение FPS, batch, окон KCP, таймаутов и лимитов без отдельных измерений.
- Одновременная переработка всех транспортов.
- Новые внешние зависимости.

## 1. Наблюдаемость и базовые измерения

### pprof сервера

Существующий HTTP-listener `stats.listen` дополнительно обслуживает стандартные handlers `net/http/pprof`:

- `/debug/pprof/`;
- `/debug/pprof/profile`;
- `/debug/pprof/heap`;
- `/debug/pprof/goroutine`.

Handlers регистрируются только если host в `stats.listen` является loopback IP. При другом адресе `/stats` продолжает работать, а pprof не регистрируется и сервер пишет одно предупреждение. Отдельный публичный порт не создаётся.

Это позволяет снять CPU и allocation profile работающего сервера через SSH без изменения firewall и без остановки туннеля.

### Метрики сервера в release gate

Локальная цель gate знает PID дочернего сервера. Для каждой ячейки S2 и S3 отчёт дополнительно получает:

- `server_cpu_seconds`: пользовательское и системное CPU время сервера за ячейку;
- `server_rss_peak_bytes`: максимальный RSS сервера за ячейку;
- `server_cpu_per_mbit`: CPU время, делённое на полезный переданный объём ячейки.

На системе без `/proc` метрики отсутствуют, а не выдаются за нули. На первом этапе они только записываются и не меняют verdict ячейки. Существующие пороги throughput, connect и памяти клиента остаются прежними.

### Benchmarks

До изменения hot path добавляются или расширяются benchmarks для:

- marshal Jitsi EndpointMessage с реальным base64 payload;
- `decodeRaw` для текущего и legacy формата;
- RTP unmarshal, reorder и сборки VP8-кадра;
- KCP write/deliver пути, если существующих замеров недостаточно для профиля.

Каждый benchmark сообщает `ns/op`, `B/op` и `allocs/op`. Базовые результаты сохраняются как артефакт сравнения, а не как новый жёсткий порог CI.

## 2. Диагностика очередей

`/stats` получает additive-поле `diagnostics`. Существующие `link`, `keys` и `total` не меняются.

Для активных peer-сессий сервер показывает только технические значения, без комнат, ключей, session ID и адресов назначения:

- число peer-сессий;
- Jitsi bridge backlog и relay bytes in flight, где доступны;
- VP8 outbound queue, текущий pacing и delivered ratio, где доступны;
- число goroutines и текущий RSS процесса.

Транспорт предоставляет snapshot через необязательный внутренний интерфейс. Транспорт без реализации интерфейса просто не возвращает соответствующие поля. Snapshot не выполняет блокирующих сетевых вызовов и не сериализует hot path.

Назначение полей: отличить CPU-bound сервер от переполненной очереди или ограничения SFU. Диагностика сама по себе не меняет pacing и flow control.

## 3. Mamba/DataChannel

Оптимизация относится к движку Jitsi, поэтому затрагивает Mamba и другие Jitsi-инстансы. VK Calls и SaluteJazz этот этап не меняет.

По CPU и allocation profile проверяются:

- `newEndpointMessage` и последующий JSON marshal;
- base64 encode/decode;
- `decodeRaw` и разбор полей входящего сообщения;
- копирования между bridge, transport и `muxconn`.

Разрешённые изменения:

- заранее выделять буфер точного или оценочного размера;
- кодировать base64 непосредственно в переиспользуемый буфер;
- убрать промежуточные строки и объекты, если это подтверждают benchmarks;
- использовать пул только с доказанным временем жизни буфера до завершения внешнего вызова.

JSON-поля, их порядок и base64 на проводе остаются совместимыми с текущим JVB. Поддержка legacy входящего формата сохраняется.

## 4. VK Calls/VP8

По профилю проверяются:

- создание `rtp.Packet` на каждый входящий пакет;
- reorder buffer и сборка кадра;
- packet buffer pool и batching;
- KCP framing, write/deliver и копирования;
- сериализация `WriteSample` через общий mutex.

Разрешённые изменения:

- переиспользование RTP-объектов и буферов с явным release после последнего потребителя;
- устранение лишних копий и повторных allocations;
- сокращение работы при batching без изменения очерёдности пакетов.

Нельзя в этом этапе менять KCP windows, FPS, batch size, blackout, pacing и логику потерь. Reorder, RED, epoch routing, per-peer lifecycle и приоритет control/ACK сохраняются.

## 5. Общий серверный путь

Если профили покажут, что основная нагрузка находится не в provider engine, а в `muxconn`, AEAD, smux или tunnel copy, следующий маленький этап оптимизирует именно найденное место. Такой этап получает собственный benchmark и применяется ко всем провайдерам только после отдельных тестов совместимости.

Этот пункт не разрешает заранее переписывать общий стек: источником изменения должен быть профиль.

## Порядок реализации

1. pprof, server metrics, diagnostics и benchmarks без изменения передачи данных.
2. Базовый gate и live-профили Mamba и VK под одинаковой нагрузкой.
3. Одно наиболее значимое изменение Mamba, отдельный коммит и сравнение.
4. Одно наиболее значимое изменение VK, отдельный коммит и сравнение.
5. Следующие изменения только по оставшемуся профилю, каждое независимо откатывается.

Несколько оптимизаций не смешиваются в одном измерении.

## Критерии принятия изменения

Для microbenchmark изменение должно улучшать хотя бы одну из метрик `ns/op`, `B/op`, `allocs/op` и не ухудшать остальные больше чем на 5 процентов без объяснения.

Для live-нагрузки выполняются чередующиеся baseline/candidate замеры на одной ВДС и одном наборе комнат. Минимум три пары замеров. Изменение принимается, если медиана показывает хотя бы один результат:

- снижение `server_cpu_per_mbit` минимум на 10 процентов;
- рост суммарного throughput минимум на 10 процентов при отсутствии роста ошибок и задержки connect.

Если live-результат остаётся в пределах разброса, оптимизация не выкатывается только ради красивого microbenchmark. Упрощение кода отдельно фиксируется, но не выдаётся за ускорение.

Обязательные условия для каждого принятого изменения:

- существующие S0-S7 не получают новых провалов;
- нет новых missed pong, reconnect, оборванных загрузок или UDP-регрессий;
- старые клиенты продолжают подключаться;
- `go test -race`, `mage check` и lint проходят.

## Live-проверка

Сначала локальный gate для Mamba/DataChannel и VK/VP8. Затем canary на Германии, по одному systemd-сервису за раз, без одновременного перезапуска остальных линий.

Проверяются:

- одиночная комната;
- существующие профили Mamba 4x, 8x и 12x;
- существующий профиль VK 4x;
- TCP download/upload и connect поверх нагрузки;
- UDP там, где транспорт его поддерживает;
- CPU, RSS, diagnostics и журнал сервера.

После подтверждения на Германии тот же бинарник устанавливается на Финляндию. SaluteJazz проходит regression gate, но не оптимизируется в этой работе.

## Откат

Wire-протокол не меняется, поэтому откат выполняется независимо на каждой ВДС заменой бинарника и перезапуском только затронутого systemd-сервиса. Клиентская версия остаётся прежней. Резервный бинарник и конфигурация сохраняются перед canary.
